# Handover — 2026-08-17 night: the revive was killing the app, and CI had stopped meaning anything

Started from one report — "the clips list for this session seems wrong" — and
ended four layers down. Five commits, all pushed, main **green** for the first
time today: `e85fc17`, `8db4855`, `31248e7`, `e5d91e8`, `d7a5087`. The phone runs
`d7a5087`, verified.

Read `android/companion/README.md` for the app and
`docs/handover/2026-08-15-evening.md` for the state of the device work; neither is
superseded by this, which is mostly about things that were quietly broken
underneath both.

## The companion app was dying every fifteen minutes, and the revive did it

The headline. `/state`'s `last_exit` showed five deaths on 2026-08-17 (20:24,
20:38, 20:54, 21:09, 21:25) plus three ANR'd restarts after them, all
`ForegroundServiceDidNotStartInTimeException`.

**`startForeground` was called only in `onCreate`.** Every
`startForegroundService()` carries its own obligation to post, and a start
delivered to a service that is **already running** skips `onCreate` — only
`onStartCommand` runs, and it never posted. So every `am start .WakeActivity`
knock on a *live* app was fatal about ten seconds later. `WakeActivity`'s own
docstring asserted the opposite ("harmless to knock on when the app is already
up… does nothing"), and that is the assumption `d7a5087` fixes; the comment now
says why it must not go back.

Since `call_guard` revives through exactly that door, **the revive was killing
the app it exists to rescue** — and each death is a hole in barge-in, because the
mic signal is this app and nothing else since Automate was retired.

Two diagnostics that made this findable, both worth reusing:

- **The crash files are better than `last_exit`.**
  `~/storage/downloads/agent-media-crash-*.txt` (the app's own
  `Crash.publishToDownloads`) carry the full trace *including* the
  `Last startServiceCommon() call for this service was made here` frame — which
  is what named `WakeActivity.onCreate:37` in every single record. `last_exit`
  gives the reason; the crash file gives the culprit.
- **`~/.local/state/sv-log/call-guard/current`** shows the loop as it happened:
  `down 31s — reviving`, `answering again (down 61s)`, over and over — plus two
  `down 270s` stretches where the 300 s rate limit left barge-in dead for four
  and a half minutes.

Verified on the device the way it should be: two knocks three seconds apart while
alive, then a wait past the deadline. `/state` kept answering, and no new exit
was recorded.

## The revive could not fire for the first five minutes after a boot

`31248e7`, found by CI and initially misdiagnosed by me as a timing flake — the
correction is worth reading in the commit. `_last_revive` was initialised to
`0.0` as though that meant "never tried", but `_now()` is `time.monotonic()`,
which counts **from boot**. On a host whose uptime is under `revive_every_s`
(300 s), the rate-limit gate reads "we tried 40 seconds ago" when nothing ever
has, and suppresses the *first* revive for the rest of that window — the boot
race, which is exactly when the app is most likely to be dead. `None` now means
never tried.

Note the interaction, because it is the reason tonight looked so bad: fixing this
makes the revive fire *more* reliably, straight into the ANR bug above. They were
found within an hour of each other by luck.

Same family as `07411e3` (a TTL comparing a monotonic clock against a file
mtime). **Treat `0.0` on a monotonic clock as a bug on sight.**

## CI had been red all day, for reasons unrelated to any of it

Five failing runs in a row, and not one was about the commit that triggered it.
That is how a signal gets trained out of people — several sessions committed on
top of a red main without noticing. `8db4855`:

- **Two tests were reading this machine's configuration.** The
  `converse_doorbell` pair asserted on the `relay-msg` argv without ever setting
  a mailbox, so they passed here — `~/.config/agent-media.env` names the box and
  sender, and something earlier in the suite loads that file into `os.environ`
  for real — and failed in CI, where `post()` finds no mailbox and returns before
  running anything. In isolation they failed locally too, which is the tell.
  `conftest.py` already scrubbed `MEDIA_REMOTE_SAY_CMD` for this exact hazard;
  the mailbox keys joined it.
- **CI runs `pytest` from `packages/core`, everyone here runs it from the repo
  root.** That difference is why no local run ever showed this. Check a green
  suite the way CI does: `cd packages/core && ../../.venv/bin/pytest -q`.

## The clip list, which is what was actually reported

`e85fc17` then `e5d91e8`. The popup's `--session` view was showing every
conversation's clips. The idle branch of `_anchor_session` resolved "which
conversation is this pane" by scanning the **50 most recent clips globally** —
fine while a pane has spoken recently. This conversation went quiet for three
days, 285 clips landed on top of it, its pane fell out of the window, the anchor
resolved to `None`, and `--session` degraded to unscoped exactly as documented.
Silently, because widening a list looks like a list.

`StateStore.session_for_pane()` asks the store instead, with no window to fall
out of. Then `e5d91e8` fixed the weaker half: ask who **owns** the pane before
who last **spoke** in it.

- Ownership needs no new writer. `claude-tmux-session-register` (agent-config's
  SessionStart hook) already writes `~/.claude/tmux-sessions/<pane>` with the
  session id, the owning `claude` pid and the cwd, keyed by pane, newest start
  wins.
- **The pid is what makes it better rather than merely different.** A registry
  entry outlives the session it names and a recycled pane will have a stale one,
  so a dead pid owns nothing and we fall back.
- **Pane ids lie.** The pane this conversation spoke from had carried twelve
  different conversations plus fifteen untagged clips. Any design that treats a
  pane id as an identity is wrong over a long enough evening.
- The empty-scope guard stays on both lookups: a live conversation that has said
  nothing would otherwise scope every popup key to an empty set, which is what a
  dead keybinding is made of.

## Things that will bite

- **Another session may be editing the same file.** `cli.py` changed under me
  mid-edit. Stage by path, check `git --no-pager diff` for work that is not yours
  before committing, and push promptly — an unpushed commit of mine was destroyed
  outright on 2026-08-14 by a peer's `git reset --hard origin/main` (recovered
  from the reflog).
- **A worktree run imports the main tree's source.** The repo `.venv` is an
  editable install, so bisecting in a worktree gives identical results at every
  commit until you set `PYTHONPATH=<worktree>/packages/core/src`. It fooled me
  for two runs and produced a confidently wrong answer.
- **`build.sh` stamps `versionName` from git** and appends `+dirty` for an
  uncommitted tree, which `/state` reports as `build`. Commit before building if
  you want that label to mean anything.
- The four tests broken earlier today by `3fafdeb` were fixed by their author in
  `9f8a14a` after I flagged them — cross-session `SendMessage` worked well for
  this, and the fix was better than either option I proposed (the filter belonged
  in `_do_replay`, not `_speech_history`, because un-counting a row silently
  shifts every index the pane lookup and the `< / >` cursor share).
