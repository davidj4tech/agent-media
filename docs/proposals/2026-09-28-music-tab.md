# A Music tab in Sasonica

Status: proposal, nothing built.
Date: 2026-09-28

David, 28 Sep 2026: *"I'm thinking about adding a music tab to sasonica either
or creating a sasonica music companion app"*. Decided: a tab, not a second app.
It can be split out later if it grows.

## Why a tab

- **One player, one handoff.** Music mostly plays on the phone's mpv
  (`tcp://…:6601`, see memory `music-phone-backend`). Sasonica's speech
  already pauses or ducks it when a reply speaks (`ba126e4`). A second app
  would need the same handoff across two processes, so it would have two
  audio-focus owners and two lock-screen players.
- **The server already has the pieces.** `media music` has play/pause/resume/
  next/prev/seek/volume/speed/like/bookmark/chapters and `status --json`, and
  `/targets` + `POST /audio-target` already choose where music plays.
- **App stays generic** (memory `app-stays-generic-server-knows-setup`). The
  tab shows what the server answers. It has no knowledge of Mopidy, mpv or
  Snapcast.
- **Upstream-mergeable.** The tab lives in fork-only files
  (`app/routes/music.tsx`, `app/components/Music*.tsx`). `Nav.tsx` gets only
  a `// Sasonica:` line for the fourth tab.

## The tab

```
┌ Home · Threads · Org · ♪ ┐
│ ▶ Title — Chapter        │  now playing: art, title/chapter, bar,
│ ⏮  ⏯  ⏭   1.0×  ♡  🔖   │  transport, speed, like, bookmark
│ Plays on: Phone ▾        │  = /targets picker (music channel)
│ ── Up next ──            │  queue; tap to jump, swipe to drop
│ ── Search ──             │  YouTube / library → play or add
│ ── Liked · Recent ──     │  from `media music likes`
└──────────────────────────┘
```

The mini player stays everywhere else. On this tab it becomes the full view.

## Server half (new, contract §6.x "Music")

- `GET /music` returns `status --json` (backend, title, chapter, pos/dur,
  paused, speed, volume, held) plus `queue` and `can` (which controls the
  live backend supports). It reads once, batched (the phone bridge takes
  ~0.8 s).
- `POST /music {action: play|pause|resume|next|prev|seek|volume|speed|like|
  bookmark|jump|remove, …}` has the same verbs as the CLI.
- `GET /music/search?q=` searches YouTube (via the phone's `play-local`
  path, since red5 is bot-walled) and the library. It is **new**: nothing in
  `media music` searches today.
- `GET /music/likes` lists liked tracks.
- Push: the reply stream's existing state events gain a `music` field, so
  the tab needs no polling.

## Order

1. `GET/POST /music` (now playing and transport). The tab shows only that
   and the where-picker, which is already enough to replace the popup.
2. The queue: read and jump, for mpv's playlist and Mopidy's tracklist.
3. Likes and recent.
4. Search. It is the only part with no backend yet.

## Open

- Should the tab appear only when music is set up (like the other opt-in
  extras), or always?
- Should the tab include books (ABS keeps them for now), or stay music only?
