# A Media tab in Sasonica

Status: proposal, nothing built.
Date: 2026-09-28

David, 28 Sep 2026: *"I'm thinking about adding a music tab to sasonica either
or creating a sasonica music companion app"*. Decided: a tab, not a second app.
It can be split out later if it grows.

Then, same day, David answered two questions:
- *"could it be possible to use the built-in player?"* Yes. Music plays in
  the app's own ExoPlayer, which the server already drives the way it drives
  mpv (`MpvServer.java` / `Media3Speech.java`, speech on :6614). Termux mpv is
  no longer needed.
- *"Maybe it should become a media tab for multiple types of media"*. The
  tab is **Media**: music first, then books and podcasts.
- *"full books. it would be nice to play them in the Sasonica player And I
  think conversations can stay in threads"*. Books play in the app's
  player, not Sasonica ABS. Replayed conversations stay on their threads and
  are not in the tab.

## Why a tab

- **One player, one handoff.** Music mostly plays on the phone's mpv
  (`tcp://…:6601`, see memory `music-phone-backend`). Sasonica's speech
  already pauses or ducks it when a reply speaks (`ba126e4`). A second app
  would need the same handoff across two processes, so it would have two
  audio-focus owners and two lock-screen players.
- **The server already has the pieces.** `media music` has play/pause/resume/
  next/prev/seek/volume/speed/like/bookmark/chapters and `status --json`, and
  `/targets` + `POST /audio-target` already choose where music plays.
- **App stays generic** (memory `app-stays-generic-server-knows-setup`). The
  tab shows what the server answers. It has no knowledge of Mopidy, mpv or
  Snapcast.
- **Upstream-mergeable.** The tab lives in fork-only files
  (`app/routes/music.tsx`, `app/components/Music*.tsx`). `Nav.tsx` gets only
  a `// Sasonica:` line for the fourth tab.

## The built-in player

The app's player becomes a second channel beside speech: an ExoPlayer
instance for media, answering the same mpv-style IPC on its own port (the
next free one beside :6614). Then:

- **No setup.** A paired phone can play media with nothing installed in
  Termux, so the tab can always show. The server's `phone` target for music
  points at the app, not at `:6601`.
- **The handoff happens inside one process.** Speech ducks music (or pauses
  a book) through the app's own audio focus, not across the bridge. The
  0.8 s bridge round trip and the doze problems of Termux mpv go away.
- **The lock screen and notification** come from a Media3 `MediaSession`,
  so there is one player there, not two.
- **What the server does not change.** It still picks what to play
  (`media music play`) and resolves YouTube, and the app plays the URL it is
  given. Termux mpv and Mopidy stay as targets (rooms, the desk) for anyone
  who has them.

Risk: YouTube URLs. Today `play-local` downloads on the phone because red5
is bot-walled. The app would need the server to hand it a file it can
fetch (the phone's cache, or a download relayed through the server) rather
than a stream URL.

## The tab

```
┌ Home · Threads · Org · ▶ ┐
│ ▶ Title — Chapter        │  now playing: art, title/chapter, bar,
│ ⏮  ⏯  ⏭   1.0×  ♡  🔖   │  transport, speed, like, bookmark
│ Plays on: Phone ▾        │  = /targets picker (music channel)
│ ── Up next ──            │  queue; tap to jump, swipe to drop
│ ── Search ──             │  YouTube / library → play or add
│ ── Liked · Recent ──     │  from `media music likes`
│ Music · Books · Podcasts │  chips filter by kind
└──────────────────────────┘
```

The mini player stays everywhere else. On this tab it becomes the full view.

## Server half (new, contract §6.x "Music")

- `GET /music` returns `status --json` (backend, title, chapter, pos/dur,
  paused, speed, volume, held) plus `queue` and `can` (which controls the
  live backend supports). It reads once, batched (the phone bridge takes
  ~0.8 s).
- `POST /music {action: play|pause|resume|next|prev|seek|volume|speed|like|
  bookmark|jump|remove, …}` has the same verbs as the CLI.
- `GET /music/search?q=` searches YouTube (via the phone's `play-local`
  path, since red5 is bot-walled) and the library. It is **new**: nothing in
  `media music` searches today.
- `GET /music/likes` lists liked tracks.
- Push: the reply stream's existing state events gain a `music` field, so
  the tab needs no polling.

## Order

0. The app's media channel (a second ExoPlayer on its own IPC port), with
   music's `phone` target pointed at it.
1. `GET/POST /music` (now playing and transport). The tab shows only that
   and the where-picker, which is already enough to replace the popup.
2. The queue: read and jump, for mpv's playlist and Mopidy's tracklist.
3. Likes and recent.
4. Search. It is the only part with no backend yet.

## Books in the Sasonica player

Books need more than music, and all of it is book-player basics:

- **Position kept per book** and resumed on open. Where the book is on the
  Audiobookshelf server, progress syncs to it, so ABS on the web or
  another device still agrees.
- **Chapters, speed, a sleep timer, skip ±30 s**, and bookmarks
  (`media music bookmark` has the model already).
- **Speech pauses a book, and does not duck it**, as the coordinator already
  does for the book channel. Inside the app this is the media player
  pausing for speech's focus and resuming after it.
- **Download for offline**, since a book is hours long and gets played away
  from Wi-Fi.

When this is in use, Sasonica ABS is retired for playback. That changes
the standing decision "Sasonica ABS stays for books". Conversations keep
being published to Audiobookshelf until then.
