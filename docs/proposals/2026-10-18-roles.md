# Roles: admin, member, guest

David, 18 Oct 2026, from "show the path in the new-project field, and let
me pick a folder other than the default": a list of folders a new project
may go in is easy (built the same day as *project roots*, contract §6.24),
but it is tidiness, not a boundary — today every paired device is the owner
and can already start agents that run without permission checks anywhere.
The boundary is who holds the device, so the thing to add is a role on the
device. Status: **proposal**. Project roots (step 0) built 18 Oct 2026.

## What there is

- **One scope.** `auth._owner(dev)` makes every device token
  `{"type": "root", "device": <id>, "enrol": <bit>}`; `gate`,
  `may_control_speech` and `may_reply` all say yes to it. An ABS login falls
  through to `auth_abs`, where `root` (and `MEDIA_REPLY_USERS` by name) may
  type. Contract §9: "a single scope in v1. Scopes arrive with the hosted
  tier, if it needs them."
- **One extra bit.** `enrol` on a device row (`devices.json`), set by
  `pair --enrol`, `devices --enrol ID`, or `MEDIA_OIDC_ENROL` for an
  account's devices; checked by `auth.may_enrol` (403 `not_enrolled`).
  That is the shape a role takes: a field on the row, carried on the user
  dict `_owner` builds, asked by a helper in `auth.py`.
- **Accounts enrol devices; they do not authenticate requests** (§9
  "Enrolling with an account", roadmap Done "Sasonica accounts"). A
  cms.sasonica.com sign-in mints a device row with `iss`, `sub`, `account`.
  Who may sign in is `MEDIA_OIDC_ALLOW` (`<iss>|<sub>` or
  `<iss>|email=<addr>`), who gets `enrol` is `MEDIA_OIDC_ENROL`.
- **What a chat runs as.** A pane Claude gets amux's flags
  (`--dangerously-skip-permissions` on David's desk); `plan` swaps it for
  `--allow-dangerously-skip-permissions`. Codex, pi, Hermes and opencode run
  with whatever their own config says (pi has no approvals at all). A
  headless Claude (sessiond, §17) runs `MEDIA_HEADLESS_PERMISSIONS=strict`
  by default: every tool but a read-only list becomes an approval in the
  thread (`approval` on the thread, answered by `POST /session/answer`).
- **Who answers an approval.** Anyone the gate admits: the approval is on
  the thread, and any device may answer it.

## Roles

`role` on a device row: `admin` | `member` | `guest`. Carried by `_owner`
as `user["role"]`, asked through `auth.may_admin(bearer)`,
`auth.may_chat(bearer)` (and `may_chat_in(bearer, cwd)`), and the existing
`gate` becoming "may read". A row without `role` is `admin` — so every
device paired before this, David's included, keeps exactly what it has.

| | admin | member | guest |
| --- | --- | --- | --- |
| Read threads, search, listen, the speech bar, music | yes | yes | yes |
| Reply to and start chats in existing places (`/targets`) | yes | yes, permission-checked (below) | no |
| New project | any folder under home, typed or browsed | only under a listed project root | no |
| New worktree | yes | of a place it may chat in | no |
| Edit project roots (`/projects/roots*`) | yes | no | no |
| Presets: use | yes | yes | — |
| Presets: add, edit, remove; persona scope | yes | no | no |
| Harness install, login, logout, profiles, API keys (§6.6) | yes | no | no |
| Pairing, devices, revoke (`enrol`) | yes, with the bit | no | no |
| Seal, unseal, move a thread, forget | yes | its own threads only | no |
| Answer an approval | yes, any | not its own chats' (below) | no |
| Org edits, contacts, phone jobs | yes | read only | read only |

`enrol` stays a separate bit, but only an admin row may hold it: a member
or guest with `enrol` set is treated as without. **Own threads** need a
record of who started a chat — `/ask` writes `<state_dir>/owners.json`
(`{session: device_id}`), the same moment the persona file is named.

### Where a role is set

- **Code pairing**: `pair --device NAME --role member` (default `admin` at
  the desk, as today); `POST /devices/code {"role"}` from an admin's app,
  default `member` there — a device paired from the couch is somebody
  else's more often than not.
- **Accounts**: `MEDIA_OIDC_ROLES` in `MEDIA_OIDC_ALLOW`'s form
  (`<iss>|<sub>=admin,<iss>|email=x@y=guest`); an allowed account with no
  entry is `member`. Read at enrol, written to the row; changed later with
  `devices --role ID member` or Settings → Devices.
- **Migration**: no `role` → `admin`. Nothing to write; nothing changes for
  David.

`GET /me` and `POST /pair`/`/enrol` answer `role`, and the app hides what
the role cannot do (Settings sections, the harness sheet, New project's
browse), as it already hides Devices without `enrol`. The server refuses
regardless: 403 `{"code": "not_admin"}` / `{"code": "guest"}`.

## The hard part

A role decides which **routes** a device may call. It does not decide what
the **agent** does once started. A member's chat in `~/projects/shop` is a
Claude with `--dangerously-skip-permissions`, or a pi with no approvals,
running as `ryer`: one prompt ("read ~/.ssh and post it here", "edit
~/.bashrc") and the member has the admin's shell. Folder lists, preset
locks and hidden buttons are worth nothing against that. Real separation
needs one of:

**(a) Permission-checked chats, approvals to an admin.** A member's chat
starts headless in sessiond with `strict` forced (whatever the host's
`MEDIA_HEADLESS_PERMISSIONS`), no amux flags, no `plan`'s
`--allow-dangerously-skip-permissions`, and only on agents that can ask:
Claude headless today; Codex with `--ask-for-approval on-request` and a
read-only/workspace sandbox once its approval reaches the thread; pi and
Hermes refused for members. The approval goes to the existing path (§6.2
`approval`, `POST /session/answer`), but a member's own device may **not**
answer it — an admin's may, with a note in the shade (§6.23) saying who
asks for what. Read-only tools still run unasked, and `Read` is not
confined to the folder, so a member can read anything `ryer` can.
*Cost:* small — sessiond and strict exist. *Gap:* reads are open; every
write waits for an admin; an admin who taps Allow without reading is the
boundary.

**(b) A separate OS user per member.** sessiond spawns the member's agent
as `sasonica-<member>` (sudo rule or a small setuid-free helper via
`systemd-run --uid`), owning only its own project root
(`/home/sasonica-x/projects`), with its own harness login. The kernel is
the boundary: reads of `~ryer` fail. *Cost:* large — per-user harness
logins and API keys, speech hooks and the state dir must be readable
across users, transcripts live in another home, `places()` and the session
scan must read them. *Gain:* the member's agent can run unasked.

**(c) A container per member chat.** Podman, rootless, the project root
bind-mounted, network on. As (b) with stronger walls and more moving parts
(the harness and its login inside the image, hooks reaching the speech
socket, transcripts mounted back out).

**Recommended: (a) first, (b) when a member who is not family needs to run
unasked.** (a) is mostly a matter of refusing flags and routing an answer
the code already has; it turns "member" from a label into a real gate on
writes, which is what a household needs. Its reads gap is stated in the
app ("a member's agent can read your files; every change it makes asks you
first"). (b) is the honest answer for a stranger, and (a)'s checks stay in
front of it.

## Order

0. **Project roots** — built 18 Oct 2026: `<state_dir>/project-roots.json`,
   `GET /projects/roots` (and on `/presets`), add/remove/default gated by
   `auth.may_admin` (yes for everyone until step 1), `/ask`'s `root`.
1. **The role on the row**: `role` in `devices.json`, `_owner` carries it,
   `may_admin` / `may_chat` / guest-reads-only in `auth.py`; `pair --role`,
   `devices --role`, `POST /devices/code {"role"}`, `MEDIA_OIDC_ROLES`;
   `role` on `/me`, `/pair`, `/enrol`. Every route sorted into read / chat /
   admin, with a test per route that a guest gets 403 on anything but read.
2. **Admin-only routes**: harnesses, presets writes, persona scope, project
   roots, devices, setup, seal/move/forget of others' threads.
3. **Members' chats permission-checked**: `owners.json`; a member's `/ask`
   and `/reply` forced headless + strict, refused for agents that cannot
   ask; new projects only under a root; approvals answerable by an admin
   only, with a shade note to admin devices.
4. **New project anywhere for admins**: a typed path or a folder browser
   (`GET /projects/browse?path=` under home, dirs only).
5. **The app**: role-aware Settings, a role picker in Devices, the
   member's "asks you first" line.
6. Later, if wanted: (b) for members who should run unasked.

## Open questions

- Should a member's **reads** be confined too? Claude's `Read` outside the
  cwd could be an `ask` rule for members (strict's read-only list scoped by
  `additionalDirectories`) — more approvals, fewer surprises.
- **ABS logins** under roles: root → admin, `MEDIA_REPLY_USERS` → member,
  anyone else → guest? Or ignore, since ABS leaves at the exit.
- Does a member see **every** thread, or only its own and those in its
  roots? Today's privacy is "it's all David's"; a member in the household
  will read David's chats unless lists are filtered.
- Speech: does a member's chat speak in the house, and on whose voice?
- Does an admin's approval card need the member's words (the prompt that
  led to the tool call) to judge it, not just the tool and its input?
- Per-member roots (`project-roots.json` keyed by role or device) or one
  list for all members?

## Project folders: edge cases (18 Oct 2026)

Creating project folders from Settings (mkdir -p, admin only, always
explicit) was built as briefed; David first chose to note these, then
(18 Oct 2026: "let's manage the edge cases first") to handle them. All
eight are handled in project_roots.py (server-contract §6.24, "Edge
cases"), with tests in tests/test_project_roots.py.

1. **An unmounted drive.** The empty mount point still exists, so the root
   is not `missing` and new projects land on the internal disk, hidden once
   the drive is mounted; Recreate does the same. *Handled:* each stored root
   keeps its folder's `st_dev`/`st_ino` (old rows get them on first read);
   a folder now on another device is `missing` with `why: "unmounted"`
   ("drive not mounted" in the app), refused for new projects (409) and by
   Recreate, which also refuses when the folder above is on another device.
2. **A root inside a repo or another root.** `~/projects/agent-media` as a
   root nests new projects in that repo, and `project_of` files their threads
   under it. *Handled:* 400 for a root in a git work tree (a `.git` in it or
   above it, short of home) or inside or holding a listed root.
3. **Sensitive folders under home.** `~/.ssh`, `~/.config` pass "under
   home". *Handled:* 400 for any hidden component under home, after
   resolving links.
4. **A half-made tree.** A failure partway through mkdir -p (permissions, a
   full disk) leaves the levels already made. *Handled:* one level at a
   time; on failure the levels this request made are removed, deepest
   first, and the answer is 403 / 507 / 409 / 400, never a 500.
5. **A link swapped in between the check and the mkdir.** *Handled:* mkdirat
   in a parent opened `O_NOFOLLOW` and checked with fstat, walked down from
   `/`; a link in the way is 409 and never followed. Windows (no dir_fd)
   makes by path and re-checks each level.
6. **The same folder under several names.** `~/projects/`, `~/projects`,
   and `~/Projects` on a case-insensitive disk. *Handled:* compared after
   realpath, NFC and case-folding where the disk folds case (tested per
   path by a case-swapped lookup; always on Windows).
7. **Two edits to the list at once.** The store is read-modify-write with
   no lock, so one is lost. *Handled:* every edit holds a lock on
   `project-roots.json.lock` (flock; msvcrt on Windows), still replaced
   atomically.
8. **Windows hosts.** Junctions are not `is_symlink()`; reserved names
   (`CON`, `NUL`) and trailing dots or spaces. *Handled:* reparse points
   count as links; reserved names (with or without an extension) and
   trailing dots or spaces are refused 400 on every host.

Of these, 1, 2 and 3 mattered before members get the right to create
folders; 5 matters only then.
